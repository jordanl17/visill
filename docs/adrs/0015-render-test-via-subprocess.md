# ADR 0015: Render-test via Python subprocess

- Status: Accepted
- Date: 2026-05-27

## Context

Phase 4 locked `render.py` as the canonical renderer. Its contract (ADR 0012): read a JSON payload on stdin, validate the schema, expand the bundled Mustache template via the vendored chevron, write HTML to stdout, write diagnostics to stderr on failure, exit non-zero on failure.

Phase 5 ships `@visill/test`, the Vitest preset consumer skills point at to verify their renderer. `createRenderTests` is the helper that drives `render.py` from Vitest. Vitest runs on Node; `render.py` runs on CPython. The preset has to bridge the two cleanly enough that a skill author writes payloads, runs `pnpm test`, and gets behaviour assertions without thinking about the bridge.

The lift source is `claude-skill-decision-tree/tests/widget/render.test.ts`, which already proved out the subprocess-per-payload shape against the same renderer contract.

## Decision

Drive `render.py` from Node via `spawnSync` on `node:child_process`, one spawn per payload. Pass the payload as stdin via `{ input: JSON.stringify(payload.input), encoding: 'utf8' }`. Read stdout, stderr, and the exit code off the result and assert against them.

Register one `it(name, ...)` per named payload inside a single `describe('render.py', ...)`. Each payload's name becomes the test name; the registration loop lives in `createRenderTests` so skill authors hand the helper a payload map and nothing else.

Payload shape:

```ts
{ input: unknown; expectFailure?: boolean; stderrContains?: string }
```

Successful payloads (default) assert exit code 0 and optionally snapshot stdout via Vitest's `toMatchFileSnapshot`. Rejection payloads (`expectFailure: true`) assert exit code is positive and, when `stderrContains` is set, that stderr contains that substring.

Module-load guard: call `spawnSync('python3', ['--version'])` once at module top. When python3 is missing, throw with a message that names `python3` explicitly, so a misconfigured host fails fast and loud rather than producing an opaque ENOENT inside every test.

Snapshots live in the consumer repo, written by Vitest under the test file. The preset ships no fixture snapshots of its own.

## Alternatives considered

- **Embed CPython via a Node binding (PythonShell, node-python).** Rejected. Adds a native build dependency, drags in install complexity, breaks across Node versions. The subprocess shape works on every host that already runs `render.py`.
- **Rewrite `render.py` in JavaScript.** Rejected. Phase 4 locked the canonical Python implementation for schema parity with the broader Anthropic skill ecosystem. A JS port doubles the maintenance surface and reintroduces drift across two languages.
- **Long-running Python service stubbed over HTTP.** Rejected. Buys nothing over subprocess spawn at the test sizes visill cares about, adds port management and lifecycle handling to the preset, and turns a 50 ms test into a process-orchestration problem.

## Consequences

- CI hosts must have `python3` on PATH. The scaffolder's `build.yml` uses `actions/setup-python`, so every skill generated by `create-visill` inherits this guarantee.
- Snapshot churn is owned by the consumer skill, in line with ADR 0022's principle that test artifacts live where they are exercised.
- Per-host `python3` path differences (some symlink `python` to `python3`, others ship `python3.12`) are accepted. The module-load guard surfaces a misconfigured environment as a clear error rather than a cascade of ENOENT failures inside individual tests.
- `@visill/test` depends on Node's `child_process` and a `python3` on PATH. Both are standard assumptions for a Node ESM package whose job is to drive a Python companion tool.
